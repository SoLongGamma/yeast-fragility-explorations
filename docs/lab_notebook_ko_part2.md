## 10. v1.0 MVP — 처음으로 "앱"을 만들다

그동안은 시뮬레이션/분석이었지 *도구*가 아니었다. 처음으로
사용자가 만질 수 있는 것을 만들었다.

- 5-state ODE (X, S, E, DO, V)
- Streamlit 단일 화면
- 입력: 현재 상태 → 출력: feed rate + DO setpoint 추천
- Grid search로 24개 (feed, DO) 조합 중 최고 선택

의도적으로 *최소*로. antifragility, Spitznagel, Monte Carlo 다 뺐다.
"일단 작동하는 것"이 목표.

**버그 하나**: Crabtree threshold가 단위 안 맞아서 ethanol이 항상 0.
0.5로 고쳐서 해결. (lab notebook의 단위 폭주 버그와 비슷한 종류)

## 11. v1.1 — Robust Optimization + 미토콘드리아 산물

MVP를 쓰다 보니 두 가지가 떠올랐다.

**(1) 미토콘드리아 산물**: 지금까지 ethanol만 추적했는데, 진짜 목표
산물은 *미토콘드리아 쪽* (citrate, succinate 등 TCA 유래)일 수 있다.
6번째 state P를 추가했다.

**(2) 로마군 원리**: "현실보다 2배 harsh하게 훈련하면?"
- 로마군이 2배 무거운 검으로 연습하듯
- Monte Carlo를 *2배 큰 변동성*에서 돌리고
- *평균*이 아니라 *p10 (최악 10%)*으로 추천을 고름

이게 *robust optimization*. 학계 표준 기법이다.

**결과 화면**: feed/DO 추천 + 수율 분포 히스토그램 + top 5 표 +
trajectory 그래프. 시각적으로 완성됨.

**버그 하나**: 히스토그램이 `pd.cut`의 구간 문자열을 Streamlit이
못 받아서 깨짐. `np.histogram`의 숫자 bin으로 고침.

## 12. "이걸 어디에 쓰지?" — 멈춤

앱이 멋지게 나왔는데, 정작 *쓸모*가 안 잡혔다.

솔직한 진단:
- 매개변수가 *교과서 평균값* → 실제 균주랑 다름
- 추천이 *검증 안 됨*
- 사용자가 *누구인지* 미정

결론: 지금 이 앱은 *교육/데모/탐색용*으로는 쓸 수 있지만,
*실제 공정 결정용*으로는 아직 못 쓴다. 부끄러운 게 아니라
대부분 학술 도구의 시작점이다.

## 13. 산업 현실 확인 — 발효 시간과 오염

질문이 떠올랐다: "실제로 70시간 넘게 발효하나? 그렇게 길면
중간에 오염되거나 망할 가능성 크지 않나?"

검색해보니 직관이 정확했다:
- 산업 발효는 산물별로 24~500시간. recombinant protein은 보통
  40~100시간. *70시간+는 흔하다*.
- **오염율: 10개 bioreactor 중 1개 (10%)**. 산업 현실.
- 오염은 주로 *DO profile의 갑작스런 하락*으로 감지된다.

이게 프로젝트의 *진짜 가치*를 건드렸다:

> "수율 최적화"보다 *"batch를 망치지 않기"*가 산업에선 더 중요하다.
> 10% 오염율 = 10개 중 1개 완전 손실. 이게 yield 5% 향상보다 크다.

그리고 이건 v0.1 ABM의 *black swan* (멸종)과 정확히 같은 것이었다.
Phase A heavy의 *culture failure rate -41%p*가 *진짜 산업 지표*와
연결된 것이다.

## 14. 개념 정리 — 못 따라온 부분 점검

너무 많은 개념이 쌓여서 한 번 멈추고 전체를 정리했다:
fed-batch, Crabtree, 5-state ODE, Monte Carlo, p10, robust
optimization, antifragility. (정리 문서 별도)

핵심 구분 3개:
- 세 모델 (ABM/ecYeast8/ODE)이 *왜 따로* 있나 → 같은 질문 다른 각도
- 측정 (Monte Carlo) vs 최적화 (grid search)
- yield 최적화 vs failure 관리

## 15. 모델 drift — 가장 날카로운 질문

"매개변수가 시간 지나면 실제랑 달라지니까 매 순간 다시 측정해야
하는 거 아니야?"

이 질문이 *제어공학의 핵심 (receding horizon)*을 스스로 도출했다.

- 효모는 시간에 따라 변한다 (노화, 적응)
- 고정 매개변수 모델은 점점 틀려진다
- 해결: 매 구간 실측 → 매개변수 갱신 → 재추천
- = 너의 앱은 *single-shot*이 아니라 *반복 호출* 도구

이게 Decision 8 (event-triggered control)과 70~100시간 발효를
12시간씩 끊어 재추천하는 그림으로 수렴한다.

## 16. 철학 전환 — "최적 찾기"에서 "아닌 쪽 거르기"로

가장 큰 방향 전환. 요구가 명확해졌다:

- 대학원 5L bioreactor용
- DO/포도당 순간순간 조절 보조
- **목표: 최대한 *아닌 쪽*을 알아내기** ← 핵심
- 실험실 각자 맞춤
- 구독 서비스

"최적 찾기"는 어렵다 (정확한 모델 필요). "아닌 쪽 거르기"는
쉽고 안전하다 (대충 모델이어도 위험 영역은 잡힌다).

비유: 보물 정확한 위치 찾기 (어려움) vs 지뢰밭 표시 (쉬움).

**Risk Map 프로토타입**:
- feed × DO 격자를 색으로 (안전🟢 / 주의🟡 / 위험🔴)
- 각 칸을 Monte Carlo로 *실패율* 측정
- 오염 event 포함 (잔류 글루코스 높거나 DO 낮으면 오염 확률↑)
- 각 실험실 데이터로 *자기 위험 지도* (calibration)

Monte Carlo가 *위험 지도의 엔진*이 됐다. "이 조합이 얼마나 자주
망하나"를 측정하는 것이 정확히 Monte Carlo가 잘하는 일이다.

## 이 구간의 서사 요약 (한 단락)

작동하는 앱을 처음 만들었고 (v1.0), robust optimization과
미토콘드리아 산물을 더했지만 (v1.1), "이걸 어디 쓰지?"에서 막혔다.
산업 현실 (70h+ 발효, 10% 오염율)을 확인하니 *yield 최적화보다
failure 관리*가 중요함을 알게 됐고, 모델 drift 문제를 짚으면서
*반복 호출 + 재측정* 구조가 필요함을 깨달았다. 결국 *"최적 찾기"에서
"아닌 쪽 거르기 (risk map)"로* 철학을 바꿨고, Monte Carlo가 그
위험 지도의 엔진이 됐다.

- 매개변수 calibration (실제 데이터 필요)
- 오염 확률 모델 정교화 (현재 임의값)
- 구독 서비스 + 프라이버시 양립 (데이터 어디 저장)
- 사용자 최종 확정 (대학원 연구실로 좁혀짐, 다만 검증 필요)

## 솔직한 메모

이 구간에서 *방향이 세 번 바뀌었다*: 최적화 → robust → risk map.
이게 혼란처럼 보이지만, 각 전환에 *이유*가 있었다. 앱을 실제로
만져보고 (v1.0), 산업 현실을 확인하고 (오염), 핵심 질문을 던지며
(drift) 방향이 좁혀졌다. 서사를 기록하는 이유는 *이 전환들이
임의가 아니었음*을 보이기 위해서다.
